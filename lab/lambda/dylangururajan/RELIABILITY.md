# CoordinateNormalizerLambda reliability evidence

## Structured logging

`CoordinateNormalizerObservability` emits one-line JSON events. The Lambda records timed storage,
lookup, and messaging operations and records request failures without logging request bodies or
exception messages. A representative event generated by the test is:

```json
{"course":"CSC5100","component":"CoordinateNormalizerLambda","service":"Storage","event":"RESULT_SAVED","status":"SUCCESS","requestId":"request-abc-123","durationMs":7}
```

`CoordinateNormalizerObservabilityTest` parses the event as JSON and verifies the five required
fields, correlation ID, nonnegative duration, and absence of simulated secret/request data.

## Interfaces and dependency injection

- `Storage.java` defines `save(id, json)` and `get(id)`.
- `CoordinateNormalizerStorage.java` contains the DynamoDB and S3 adapter.
- `Messaging.java` defines `publish(json)`.
- `CoordinateNormalizerMessaging.java` contains the SNS and SQS adapter.
- `CoordinateNormalizerLambda` accepts `Storage` and `Messaging` through package-private
  constructors, while its public constructor creates the production adapters.

The handler therefore coordinates application behavior against contracts rather than AWS SDK
clients. Tests inject in-memory fakes and do not need AWS credentials or network access.

## Controlled failure analysis

`messagingFailureReports500AfterStorageCompleted` injects a messaging dependency that always
fails. Normalization and the storage save complete once, messaging fails, and the Lambda returns
HTTP 500. This is a partial completion: the result may be present in S3/DynamoDB even though no
message was published and the caller sees a failure. The complementary
`storageFailurePreventsMessagingFromRunning` test verifies that a storage failure returns HTTP 500
and prevents the later messaging operation.

## Bounded retry and idempotency

The selected retry operation is `Storage.get`, an idempotent read. `RetryingStorage` delegates
writes once and applies `RetryExecutor` only to lookups. The executor permits no more than three
total attempts, retries only failures accepted by its classifier, returns immediately after
success, and uses an injected no-op delay in tests.

Transient transport or service-unavailable failures are eligible; invalid input and authorization
failures are not. A read has no duplicate write or publication effect, though it could repeat read
side effects such as metering. The production constructor deliberately uses the AWS adapter
directly because AWS SDK v2 already has its own retry policy; this prevents the application policy
from multiplying SDK attempts. If a write or publish were retried instead, the result UUID should
be used as an idempotency key (or an SQS FIFO deduplication ID) so a lost response cannot cause a
duplicate effect.

## CloudWatch discussion

An application-level failure is one the handler catches and converts to a response such as HTTP
500; because the invocation completed normally from Lambda's perspective, it may not increase the
Lambda `Errors` metric. A Lambda execution error is an uncaught exception, timeout, or runtime
failure and does increase `Errors`. Structured application logs identify the component, operation,
status, request ID, and failure type, while Lambda metrics show aggregate invocation count, runtime
errors, and duration. Both are needed because metrics reveal scope and trends while correlated logs
explain a particular request.

No dashboard observation is claimed here: the local reliability changes were not deployed, and no
public dashboard URL was present in the repository. Add the dashboard screenshot or copied
timestamp/request information to the pull request after observing the existing deployed Lambda.

## Local regression evidence

The POST regression coverage includes the API Gateway HTTP API v2 event shape, POST coordinates in
query parameters, and a direct Lambda event. Invalid requests print both the exception message and
stack trace to standard output for CloudWatch diagnosis. Local adapter tests also verify that the
same result JSON is written to S3 and DynamoDB and published to SNS and SQS.

Commands run after the refactor:

```text
mvn -Dtest='CoordinateNormalizer*Test' test
Tests run: 23, Failures: 0, Errors: 0, Skipped: 0

mvn test
Tests run: 88, Failures: 0, Errors: 0, Skipped: 0
```

The retry tests show three attempts for fail-twice-then-succeed, three attempts for exhaustion, and
one attempt for a non-retryable failure.
